# Implementation Planning

**Prompt version:** 1.7

## Role
You are a technical project manager translating approved documentation into an implementation roadmap.

## Planning hierarchy
This workflow's planning levels are:

```
Project
 └── Milestone          (this phase — one at a time, see milestone-status.md)
      └── Epic           (this phase — one per module/major capability)
           └── Task           (this phase defines it; 8-implementation/1-implement-task.md executes it)
                └── Todo            (1-implement-task.md, broken out during implementation)

Sprint (7-sprint-planning/1-sprint-planning.md) is a time-boxed slice: it pulls Tasks
from one or more Epics, but always from a single active Milestone.
```

## Objective
Create Milestones, Epics, and a full Task list with dependencies, derived entirely from the now-current documentation in `project-docs/approved-docs/docs-kit/`. Also initialize the milestone status tracker used to gate work to one milestone at a time.

## Re-run after launch, scoped to a new milestone
This prompt isn't only for the project's initial plan. Once the first milestone is `Released`, `project-docs/prompts/12-maintenance/2-feature-request.md` re-runs it scoped to just the new milestone it created for a batch of post-launch features — same Instructions below, applied to the new milestone's epics/tasks only, not a re-derivation of the whole project. On that first run only, also create `project-docs/claude-docs/plan/epics.md`'s standing **Maintenance** epic (no milestone assignment — it persists across every milestone) for small post-launch fixes routed here by `12-maintenance/1-triage.md` that don't warrant their own epic or milestone; skip creating it again on later re-runs, it already exists.

## Re-run scoped to a single module (just-in-time documentation)
This prompt also re-runs mid-project, scoped to just one module, as the last step of the just-in-time module documentation gate in `7-sprint-planning/1-sprint-planning.md` step 2a. On that scoped run: skip steps 1, 7, 9, 10 (milestones, `milestone-status.md`, `raid-log.md`/`tech-debt-register.md`, `lifecycle-dashboard.md` already exist from the initial run) and apply steps 2–6 and 8 to just this module's epic(s) — deriving its real Task list now that `docs-kit/5-modules/<module>/` finally exists, replacing the empty/TBD placeholder task list that module's epic was given on the initial run (see Instructions step 2 below).

## Inputs
- `project-docs/sot-docs/index.md` and everything it points to under `project-docs/approved-docs/docs-kit/` (`1-project`, `2-database`, `3-api`, `4-ui`, `6-development`). `5-modules/<module>/` is **not** a required input on the initial run — under the default Milestone 2/3+ structure, module documentation is generated just-in-time (see `7-sprint-planning/1-sprint-planning.md` step 2a), so it won't exist yet for any module the first time this prompt runs. It becomes an input only on a module-scoped re-run (see above), for that one module.

## Instructions
1. Derive Milestones from `docs-kit/1-project/2-requirements.md` and `docs-kit/1-project/3-feature-breakdown.md`. **Default milestone structure, unless the user directs otherwise, is horizontal by layer for the first two milestones, then vertical per module after:**
   - **Milestone 1 — Environment setup.** Install and wire the chosen tech stack (language/runtime, framework, database engine, package manager, dev-server) so the project runs locally. No feature or UI work. Exempt from the demoable-slice rule below; its "done" signal is the stack running, not something to click through.
   - **Milestone 2 — UI, all modules, static/mock data.** Build every page for every module/screen in `docs-kit/1-project/3-feature-breakdown.md` (including auth screens and the dashboard/app shell) using static/mock data shaped to match the already-approved `docs-kit/2-database/` and `docs-kit/3-api/` documents — no real API or business logic wired yet. This milestone is what makes the **Module Design-First Strategy** in `8-implementation/1-implement-task.md` the default flow rather than an opt-in: every module's UI-Design epic lives here.
   - **Milestone 3 onward — Backend/API per module, layered on.** Each subsequent milestone wires the real backend/API for one module (or a small dependency-ordered group of modules) onto its already-approved Milestone 2 UI, in dependency order (`docs-kit/2-database/` → `docs-kit/3-api/` → wiring). From here on, each milestone **is** a vertical, demoable slice — the module goes from "looks real" to "is real."

   Milestones 2+ still follow the demoable-slice principle within their own scope (Milestone 2's slice is "the whole app is clickable end-to-end on fake data"; each Milestone 3+ slice is "this module is now real"). If the user directs a fully vertical structure instead (each milestone = one module's full stack, UI and backend together, no separate UI-only milestone), skip this default and derive milestones the traditional way — the Design-First Strategy then reverts to its per-module opt-in ask.
2. Derive Epics from `project-docs/claude-docs/analysis/module-list.md` (not `docs-kit/5-modules/<module>/`, which doesn't exist yet on the initial run — see "Inputs" above) and from cross-cutting capabilities (e.g. "Auth", "Dashboard Shell"). Every module epic still gets created now, from its module-list entry alone, so `7-sprint-planning/1-sprint-planning.md` has an epic to select into a sprint — its detailed Task list just stays empty/TBD (see step 3) until that module's just-in-time documentation gate fills it in later. Scope each epic to fit inside one milestone — if a module's full feature set spans multiple milestones (e.g. "Auth: Login" now, "Auth: Password Reset" later), split it into separate epics per milestone rather than one epic straddling two milestones. Assign each epic to the milestone it belongs to. **Always include an explicit "App Shell / Chrome" epic** (branding, navigation shell, header/sidebar layout, cross-page-consistent framing) owned by whichever milestone first renders a real authenticated screen — this is deliberately not left implicit inside a per-module epic, because chrome that "isn't this module's job" in every module's own review is chrome nobody ever owns, and it only gets fixed reactively when a user visually compares the build against the design source. **Under the default Milestone 2/3+ structure (step 1):** every module (plus App Shell/Chrome) gets a `<Module> — UI Design` epic under Milestone 2, and a separate `<Module> — Backend/API` epic under whichever Milestone 3+ it's scheduled in — these epics use the Design Status field (see Output below) by default, since Design-First is mandatory under this structure, not opt-in.
3. **For a module epic whose `docs-kit/5-modules/<module>/` doesn't exist yet (the normal case on the initial run, under the default just-in-time flow — see "Inputs" above): leave its Task list empty, marked `TBD — awaiting just-in-time module documentation`, rather than guessing tasks from an undocumented module.** That epic still gets its milestone assignment, status (`Not Started`), and Design Status (blank) set normally — only its Task breakdown is deferred. Skip straight to step 7 for that epic; steps 3–6 below don't apply to it until the module-scoped re-run (see "Re-run scoped to a single module" above) fills in its real tasks. For every epic whose module docs already exist (global/cross-cutting epics always; module epics on a scoped re-run), break each epic into Tasks small enough to implement in a single sitting (a few hours to a day), and make sure each milestone's tasks cover the full vertical (schema → API → UI) needed for its slice to actually run, not just one layer. Each task should reference the exact source file/section under `docs-kit/` it implements. If something is too large for one task, split it rather than leaving it as an umbrella item. Before finalizing the task list, cross-check it against any deferred/nice-to-have list in `sot-docs/raw/` — don't create a task for something the SoT already marked as explicitly out of scope; that gets caught here, not discovered and cancelled mid-sprint. **Size tasks by user-facing capability, not by CRUD verb or implementation layer** — splitting "create X" / "edit X" / "delete X" into separate tasks (or splitting a single UI feature's "component" from its "wiring/logic") routinely produces tasks that collapse into one during implementation, because the pieces aren't independently useful or testable on their own. If two candidate tasks would only be demoable/testable together, they're one task. **Exception:** if a module adopts the design-first strategy (`8-implementation/1-implement-task.md`) — the default for every module under this template's Milestone 2/3+ structure (step 1), optional otherwise — its UI-with-mock-data work and its real backend/API work are deliberately two separate tasks (e.g. `<Module> — UI Design`, `<Module> — Backend/API`), because a genuine developer-review pause sits between them and the developer may pick a different module's backend to build next rather than continuing immediately — this is the one case where splitting is correct, not a sign of mis-sized tasks. **Every module epic's task list must include a seed/demo-data task scoped to realistic content** (real-sounding names/subjects/values derived from the BRD's own domain, not placeholder strings like "Test Item 1") — demo-data realism found out reactively, only when someone explicitly asks for a demo, means every earlier walkthrough was done against data too thin to catch real UI/UX problems (truncated text, empty-state styling, sort/filter behavior on a real distribution of values). A faker library (e.g. `@faker-js/faker`, or this stack's equivalent) is fine for generic fields (names, emails, addresses, dates) but never for domain-specific content (task/project titles, statuses, business-rule-driven values) — see `8-implementation/1-implement-task.md` step 2's Module Design-First Strategy for the same split applied to a module's static/mock UI pages, which should reuse this same dataset rather than generating a second, inconsistent one.
4. Map dependencies between tasks (e.g., `docs-kit/2-database/1-database-design.md` work before `docs-kit/3-api/` work that queries it; API work before UI work that consumes it) — including dependencies that cross epic boundaries.
4a. **Traceability completeness check — do this before finalizing the task list, not after.** Walk every entity/field in `2-database/`, every endpoint in `3-api/`, and — for whichever modules have documentation at the point this step runs (all of them, on a module-scoped re-run; none of them, on the initial run under the default JIT flow) — every rule in that module's `3-business-rules.md` and every element in its `9-ui.md`, and confirm each one maps to at least one task above. Anything documented but with no owning task is a real gap — either add a task for it now, or if it's genuinely out of scope, note why (and confirm that matches a stated scope decision, not silent omission). A doc entity that sits unbuilt for dozens of tasks because nothing ever checked for orphaned doc content is the exact failure mode this step exists to catch — it should never again take a much later task's own scope forcing the issue to notice something was specified from the very first draft and never built.
5. Provide a rough size/effort estimate per task (S/M/L or time range) — flag anything too large to estimate confidently as needing to be split further.
6. For each task, list the **files/folders it's expected to touch** (best guess is fine — exact paths aren't known until implementation, but name the area: e.g. "auth migration + `models/User`", "`routes/auth.*`", "`components/LoginForm`"). This field is required, not optional, whenever more than one developer (or session) works on the project — it's what `7-sprint-planning/1-sprint-planning.md` uses to mark which tasks are safe to hand to different developers at the same time: two tasks with no shared files and no dependency between them can run in parallel; two tasks that touch the same file/folder cannot, regardless of what their dependency graph says. For a single solo developer, this field can still be filled in loosely but doesn't affect anything — implement tasks in dependency order and move on.
7. Initialize `project-docs/claude-docs/plan/milestone-status.md`: one row per milestone, status `Not Started`, in build order. Only the first milestone starts as `Not Started` and ready to begin — later phases update this file as work progresses.
8. Initialize a `status` field on every epic in `epics.md`, starting at `Not Started`. See "Status Tracking" below — every level of the tree keeps a status from here on.
9. Initialize `project-docs/claude-docs/plan/raid-log.md` (empty Risks/Assumptions/Issues/Dependencies table) and `project-docs/claude-docs/plan/tech-debt-register.md` (empty) — `7-sprint-planning/` and `8-implementation/2-code-review.md` write to these throughout the project; they should exist from the start rather than getting created ad hoc the first time something needs logging.
10. Initialize `project-docs/claude-docs/plan/lifecycle-dashboard.md` — a single-page rollup of milestone/epic/sprint status, open risks (from `raid-log.md`), and outstanding tech debt (from `tech-debt-register.md`), so a stakeholder gets the whole project's state without reading every plan file individually. Every phase from here on that changes a status this dashboard summarizes (`7-sprint-planning/`, `8-implementation/`, `10-release/1-release.md`) should refresh it, not just its own source file. For a visual, browser-viewable version of the same rollup, run `11-dashboard/1-generate-dashboard.md` any time — it reads the same source files and regenerates a static HTML page rather than a markdown one.

## Output
- `project-docs/claude-docs/plan/milestones.md`
- `project-docs/claude-docs/plan/epics.md` — every epic with ID, milestone, module/document reference, description, **status** (`Not Started` / `In Progress` / `Complete`, starting `Not Started`), and **Design Status** (blank / `Pending Review` / `Approved` — used by every `<Module> — UI Design` / `<Module> — Backend/API` epic pair under the default Milestone 2/3+ structure, and by any other epic that separately opts into the design-first strategy in `8-implementation/1-implement-task.md`'s "Module Design-First Strategy" section; blank means design work hasn't started yet, not that the strategy was declined)
- `project-docs/claude-docs/plan/task-list.md` — every task with: ID, epic, milestone, description, source reference into `docs-kit/`, dependencies, estimate, file/folder footprint, **status** (`Available` / `Claimed` / `In Progress` / `Blocked` / `Done` / `Cancelled`, starting `Available`), and **Assigned To** (empty until claimed, then the claiming developer's name — see "Multiple developers working in parallel" in `prompts/README.md`)
- `project-docs/claude-docs/plan/dependencies.md` — dependency graph in plain-language or Mermaid form
- `project-docs/claude-docs/plan/milestone-status.md` — milestone build order and status (`Not Started` / `In Progress` / `Complete` / `Released`)
- `project-docs/claude-docs/plan/raid-log.md`, `tech-debt-register.md`, `lifecycle-dashboard.md` — initialized empty, maintained by later phases

## Status Tracking
Every level of the hierarchy carries a status, and each level's status is a rollup of the level below it — from here on, any phase that changes a Task's status must also update its Epic and Sprint, so a single glance at any file tells you what's actually done:

```
Todo    — checkbox per item in {{task_id}}-todos.md (checked = done)
Task    — task-list.md + sprint file: Available / Claimed / In Progress / Blocked / Done / Cancelled
Epic    — epics.md: Not Started (no tasks started) / In Progress (some but not all Done, excluding Cancelled) / Complete —
  - **For a `<Module> — Backend/API` epic** (or a module's single epic under a fully vertical structure): all non-Cancelled tasks Done **and** `9-sync-docs/2-module-completion-review.md` has passed clean for this epic **and** the user has confirmed the module's real functionality live in a browser per that prompt's closing step — Claude's own automated checks passing is necessary but not sufficient here. This is the epic where real code exists to check design fidelity against, trace data-flow through, and verify docs-vs-code against — `9-sync-docs/2-module-completion-review.md` is scoped to run here, not against the UI-only epic below.
  - **For a `<Module> — UI Design` epic**: all non-Cancelled tasks Done **and** Design Status is `Approved` (per the developer's live-browser review loop in `8-implementation/1-implement-task.md`'s Module Design-First Strategy) is sufficient. Do **not** also require `9-sync-docs/2-module-completion-review.md` here — its data-flow and docs-vs-code checks need real backend code that doesn't exist yet at this stage; running it against mock-only pages would be premature. The Design Status review loop already serves as this epic's completion gate.
  - **For a non-module epic** (Environment Setup, App Shell/Chrome, the standing Maintenance epic, or any other epic with no corresponding `docs-kit/5-modules/<slug>/`): all non-Cancelled tasks Done is sufficient — `9-sync-docs/2-module-completion-review.md` cannot run against an epic with no module to review, so don't require it. Don't let this become a loophole for module work, though — an epic is only "non-module" if it genuinely has no `5-modules/` counterpart, not because someone skipped documenting one.
Sprint  — sprint-{{n}}.md: Not Started / In Progress / Complete (same rollup rule, over its own task subset)
Milestone — milestone-status.md: Not Started / In Progress / Complete (all epics Complete) / Released (1-release.md ran)
```

A `Blocked` task holds its Epic and Sprint at `In Progress` (never `Complete`) until it's unblocked and Done — this is intentional, so a blocked item can never silently disappear from the status picture. A `Cancelled` task is excluded from its Epic/Sprint's completion rollup entirely (neither blocking `Complete` nor counted as work done) — use it when a task is no longer wanted, not as a substitute for `Blocked` or `Done`. `8-implementation/1-implement-task.md` and `2-code-review.md` are responsible for keeping Epic and Sprint status current whenever a task's status changes; `7-sprint-planning/1-sprint-planning.md` reads Epic status (not raw tasks) to decide whether a Milestone is done and whether it's time to tell the user to run `10-release/1-release.md`.

## Keeping plan files recoverable
`milestones.md`, `epics.md`, `task-list.md`, `dependencies.md`, `milestone-status.md`, and every `sprints/sprint-{{n}}.md` are hand-edited by multiple phases throughout the project — they're load-bearing state, not disposable notes. Make sure `project-docs/claude-docs/` is committed to version control alongside code (it already should be, per `docs-kit/6-development/2-folder-structure.md`'s "files to commit" list) so a bad edit to any of these files is recoverable via normal git history — there is no other backup mechanism for them.

## Guardrails
- Every task must trace to a document under `project-docs/approved-docs/docs-kit/`, not to assumptions made during planning.
- Every task belongs to exactly one epic, and every epic to exactly one milestone.
- Don't build a milestone that's purely one layer (e.g. only schema, or only API) — if a milestone's tasks don't add up to something the user can run and check, it's sliced wrong; rebalance it into a full vertical.
- Don't schedule tasks into sprints here — that's `7-sprint-planning/`. Don't break tasks into Todos here — that happens during `8-implementation/1-implement-task.md`, per task, right before writing code.
