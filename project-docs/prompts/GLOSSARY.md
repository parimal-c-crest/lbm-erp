# Glossary — Plain-Language Definitions

> Referenced from `prompts/README.md`'s "Glossary" section. Every term this workflow uses that isn't everyday English gets defined here once — so it can be pointed to instead of re-explained differently each time.

| Term | Plain-language meaning |
|---|---|
| **SoT (Source of Truth)** | The original material you provided — your notes, requirements doc, vision doc, existing screenshots. Everything else in `project-docs/` is built from this, and it's always the final word if something else seems to disagree with it. |
| **docs-kit** | The finished, approved documentation for your project — requirements, database design, API design, UI design, per-feature specs, dev practices. Lives in `project-docs/approved-docs/docs-kit/`. |
| **Draft** | A document that's been written but not yet reviewed/approved. Lives in `project-docs/claude-docs/drafts/` until it's checked and promoted into `docs-kit/`. |
| **Milestone** | A big chunk of the project that ends with something you can actually open and click through — e.g. "users can log in and see a dashboard." Milestones happen one at a time, in order. |
| **Epic** | A feature-sized piece of work inside a milestone — e.g. "Login," "Password Reset," "Order Management." One epic belongs to exactly one milestone. |
| **Task** | A single piece of implementation work small enough to do in a sitting (a few hours to a day) — e.g. "build the login API endpoint." One task belongs to exactly one epic. |
| **Todo** | The smallest checklist item, broken out right before actually writing code for one task. |
| **Sprint** | A time-boxed batch of tasks pulled from the current milestone's epics — planned one sprint at a time, not all upfront, because task priority and estimates depend on what's actually happened so far. |
| **Status rollup** | How "done-ness" flows upward: all Todos done → Task done; all Tasks done → Epic done; all Epics done → Milestone done. A single blocked item anywhere holds its whole chain at "In Progress," so nothing can look finished while something inside it is stuck. |
| **RAID log** | A running list of open Risks, Assumptions, Issues, and Dependencies for the project — reviewed every sprint so nothing gets forgotten. |
| **Tech debt register** | A list of deliberate shortcuts taken to move faster, that someone chose to accept rather than fix immediately — tracked so they don't get forgotten forever. |
| **Definition of Ready (DoR)** | The checklist a task must pass before it's allowed into a sprint — clear description, no unanswered questions, dependencies already done. Stops half-defined work from starting and stalling mid-sprint. |
| **`[NEEDS INPUT: ...]` marker** | A spot in a document where something couldn't be filled in because the answer isn't known yet — a flag for you to resolve, not something to ignore. |
| **`[Assumption: ...]` marker** | A spot where the user was explicitly asked and told Claude to use its own judgment, rather than a silent guess — labeled so the deferred call stays visible for later reference. In `3-document-generate/` (document generation, since v8), this marker only appears *after* asking; nothing gets written on a guess the user hasn't seen. |
| **Non-functional requirement (NFR)** | A quality target rather than a feature — how fast, how available, how secure — as opposed to "what it does." |
| **Threat model** | A document listing what could go wrong from a security angle (who might attack it, how, what's protected against it) for the whole system. |
| **Cross-cutting** | Something that applies across every feature/module rather than belonging to just one — e.g. performance targets or security rules apply to the whole app, not one screen. |
| **Assigned To** | A field on a task/sprint entry naming which developer claimed it — used once more than one developer is on the project, so two people don't accidentally grab the same task. |
| **Parallel-safe batch** | A group of tasks that don't share files and don't depend on each other, so different developers can work on them at the same time without stepping on each other. |
| **Design Status** | A field on a module's epic (`Pending Review` / `Approved`) tracking whether its pages (built with fake/sample data) have been reviewed and approved by the developer, before real backend/API work on that module is allowed to start. Used by every module by default under this template's Milestone 2 (UI-only) / Milestone 3+ (backend) structure; optional otherwise. See `8-implementation/1-implement-task.md`'s "Module Design-First Strategy." |
| **Batch generation** | Writing every document in a category (or module) in one run of one prompt file, instead of running a separate prompt per document. Every `3-document-generate/<category>/` folder is now one batch file (e.g. `03-api/api.md` covers all 10 API documents). Introduced in v7 to cut the number of stop-and-confirm round trips per category. Not to be confused with **Parallel-safe batch** above, which is about implementation tasks, not document generation. |
| **Wave** | Within `06-development/development.md`, a subgroup of that category's documents that share a dependency gate — the *early wave* (6 documents) has no dependency on modules and runs upfront, alongside `02`–`04`; the *late wave* (4 documents) is just-in-time, scoped and updated one module at a time as each module's own documentation is generated, rather than waiting for every module to finish. Each wave-run is still one batch, one confirmation — the split exists because of the dependency, not as a size reduction. |
| **Just-in-time (JIT) module documentation** | Since v8, `5-modules/modules.md` (and `06-development/development.md`'s late wave) no longer generate for every module upfront — they're triggered per module by `7-sprint-planning/1-sprint-planning.md` step 2a, the first time that module's epic is a sprint candidate. Spreads module documentation across the project's real build timeline instead of front-loading all of it before any module is touched. See `prompts/README.md`'s "Just-in-time module documentation" section. |
| **User browser acceptance** | The required manual check, added in v8, where the developer opens the running app in a real browser and confirms it actually works — used twice: after a module's static/mock UI pages are built (`8-implementation/1-implement-task.md`'s Module Design-First Strategy, before Design Status can become `Approved`), and after a module's real backend is implemented (`9-sync-docs/2-module-completion-review.md`, before the epic can be marked `Complete`). Not satisfied by Claude describing or summarizing what was built — the developer has to click through it themselves, and any issue found gets fixed and re-checked until they confirm it. |
| **Pre-generation gap sweep** | The step inside `1-discovery/6-gap-analysis.md` that walks every template's section headings across all seven categories and asks, for this project, whether each section is likely answerable yet — surfacing predictable gaps as questions *before* any document gets drafted, instead of discovering them mid-batch. Doesn't catch everything; genuinely unpredictable gaps still surface later as `[NEEDS INPUT]`/`[Assumption]` markers during generation. |
| **Triage lane** | One of six categories `12-maintenance/1-triage.md` sorts an incoming post-launch item into — production incident, requirement change, new feature, non-urgent defect, doc/code drift, or routine upkeep — each handing off to a different prompt or task type. |
| **Intake log** | `project-docs/claude-docs/plan/intake-log.md` — one dated row per item triage has ever classified, what it was, which lane it went to, and why. The concrete record behind `10-release/1-release.md`'s "lightweight intake process." |
| **Delta documentation plan** | A dated section appended to the existing `documentation-plan.md` by `12-maintenance/2-feature-request.md`, listing only the documents one post-launch feature adds or changes — not a new plan file, and not a re-derivation of the whole project's plan. |
| **Maintenance epic** | A standing epic, created once the first time `6-implementation-plan/1-implementation-plan.md` runs post-launch, that never belongs to a milestone and never closes — small post-launch fixes routed there by triage land as tasks under it instead of needing their own milestone. |
| **Module field extraction** | Since v9, step 0 of a module's JIT gate (`05-modules/0-field-extraction.md`) — an exhaustive, individually-listed field and business-rule catalog for one module, produced before any of its 11 documents are drafted. Supports two origins: extracted from an existing system's real source code and live database (every fact cited to file:line/query), or derived from the SoT plus direct questions for a genuinely new module. Output lives in `project-docs/claude-docs/analysis/module-field-extraction/<module-slug>/`, separate from the 11-file deliverable it feeds. |
| **Underspecified** | A third confidence tag (alongside `Confirmed` and `Inferred`) used in module field extraction. Means the source shows a field or rule exists but doesn't describe it well enough to fill in confidently — distinct from `Inferred` (deduced from context, not directly stated) because the gap here is incompleteness, not ambiguity, and needs follow-up input rather than a best-guess read. |
