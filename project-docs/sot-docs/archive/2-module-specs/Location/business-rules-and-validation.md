# Location — Business Rules & Validation

> Every rule gets a stable ID (e.g. <MOD>-RULE-001) so Stage 4's test docs can trace back to it.

Source: `blueprint/module/Location/02-validation-rules.md` via
`docs_from_blueprint/module/Location/03-business-rules-and-validation.md`. The source blueprint
catalogs 31 numbered rules (`LOC-VAL-001`-`LOC-VAL-031`), renumbered `LOC-RULE-001`-`LOC-RULE-031`
below with the original ID preserved in the Statement text for cross-reference. Every rule below was
established by a direct read of the module's save-orchestration, QoH-write, and part-supersession
code — Confidence is `Confirmed` throughout unless noted otherwise.

**Four headline findings this rule catalog is built around** (every rule below should be read
against these):
1. **No negative-QoH guard exists anywhere in this module.** Every quantity-on-hand-writing path
   (manual ajax adjustment, the mislabeled "kit" ajax adjustment, the generic field-level ajax save,
   the part-supersession merge) writes whatever value it is given straight to the field with no floor
   check. The only non-negative clamp anywhere in the module protects Total Available, not QoH itself.
2. **Concurrent-update protection is a session-mismatch ping, not a lock.** It catches a stale
   browser tab, not two genuinely simultaneous submits from the same valid session.
3. **The endpoint the kit-adjustment UI actually calls performs zero kit-component propagation**
   despite its filename and the client-side function name that calls it.
4. **Part-supersession QoH/order handling touches no open Sales Order/Purchase Order lines** still
   referencing the superseded product id — this module's own code cannot confirm what an in-flight
   order against a just-superseded part experiences.

## Open Questions

- **The top-level dispatch script for the part-supersession linking group (LOC-RULE-018 to 021)
  interpolates a request-supplied id directly into raw SQL with no sanitization — a confirmed SQL
  injection.** Cross-referenced in `risks-and-open-questions.md`. The caller(s) of the "check" function
  in LOC-RULE-021 were never located in any pass.
- **The generic delete/permission-check function LOC-RULE-022's Delete endpoint calls performs the
  actual delete/permission logic and was never read in any pass** — whether deleting a Location with
  non-zero QoH, open orders, or WMS placements is blocked, warned, or silently allowed is unconfirmed.
- **The WMS tote/pick-list branches of the QoH-adjustment endpoint (LOC-RULE-010) write to WMS-owned
  tables with no visible quantity validation either**, but those tables are outside this module's own
  inventory scope and were not traced further.
- **Several field-name-routing helper functions called from the field-level ajax save endpoint
  (LOC-RULE-030) are defined elsewhere and were not opened** — no claims are made about their own
  internal validation. Several branches build SQL with the field **name** itself concatenated directly
  into the query string — the field's value is parameterized but its name is not — a confirmed
  SQL-injection pattern once traced against an attacker-controllable request value.
- **Whether any of the confirmed SQL-injection points above (LOC-RULE-010, LOC-RULE-018-021 group,
  LOC-RULE-030) have an access-control layer above the request-dispatch level** was not traced end to
  end — see `risks-and-open-questions.md` §9.4 for the full framing of this as the single
  highest-priority unresolved question in this module's specification.
