# Location — Risks & Open Questions

Source: `blueprint/module/Location/07-risk-findings.md` (risk re-verification pass) +
`08-consolidation-review.md` (final consolidation/master rollup) via
`docs_from_blueprint/module/Location/09-risks-and-open-questions.md`. Original register numbering
(1-22) preserved inline in each `LOC-RISK-###` row's Finding text for cross-reference.

**This module carries the broadest correctness/security blast radius of any module blueprinted in
this series to date.** Unlike other already-blueprinted modules' Critical findings, each anchored to a
bounded attack surface or a specific incident, this module's core defect (unbounded negative
quantity-on-hand, with no system-level guard at any of four independent write paths) sits directly in
the path of every sale, receipt, and transfer in the entire ERP, not merely in one module's own
transaction flow. **The five Critical findings below are flagged by the source blueprint as needing
legacy-system remediation now, independent of any rewrite timeline** — restated here because a reader
arriving at this file without the fuller context in `build-guidance.md` §10.6 could otherwise assume
these risks stay dormant until a rewrite/cutover happens; they do not.

## Risk Register

| ID | Finding | Severity | Impact | Source |
|---|---|---|---|---|
| LOC-RISK-001 | No negative-QoH guard exists anywhere in the module — all four independent write paths into the quantity-on-hand field (manual adjustment, the mislabeled "kit" adjustment, the generic field-level ajax save, the part-supersession merge) can drive it negative with zero system-level prevention. Re-confirmed by a dedicated final re-verification tracing all four write paths a second time. | Critical | The module's highest-blast-radius finding: a corrupted/negative on-hand-quantity figure at even one product/branch silently propagates into every downstream sale-eligibility check, reorder calculation, and financial-valuation figure that reads that quantity afterward, across modules well outside Location. | `07-risk-findings.md` §3/§4 |
| LOC-RISK-002 | SQL injection in the part-supersession linking engine — a request-supplied id is spliced unquoted, unescaped, unparameterized across seven statements including two write statements, with no visible role/permission gate in the same file. | Critical | Direct database write exposure on the same code path as LOC-RISK-024/025 (the quantity-merge/discard mutations). | `07-risk-findings.md` §4 |
| LOC-RISK-003 | SQL injection via unvalidated field-name splice in the generic field-save ajax endpoint — six independent request branches use a request-supplied value as the raw SQL **column name** itself, value correctly parameterized but column not, no whitelist anywhere; one branch targets the branch-header table itself, not just the high-cardinality Product-at-Location table. | Critical | Attacker-controllable column targeting, reachable via the module's highest-traffic write path (every inline field edit on the Products page's Location panel). | `07-risk-findings.md` §4 |
| LOC-RISK-004 | SQL injection in the Lost Sale Log Report's four inline-edit write statements — every request-derived value is spliced unescaped into raw SQL with no parameterization, reachable by any staff user with access to the home-page report portlet, not an admin-only surface. Newly catalogued by the risk-verification pass itself — not flagged by any earlier pass. | Critical | Reachable by ordinary staff, not just admins. | `07-risk-findings.md` §4 |
| LOC-RISK-005 | SQL injection in the plain and "kit" QoH-adjustment endpoints' direct QoH write — a request-supplied value is concatenated unescaped into a query fragment before the query string is assembled, landing outside the otherwise-present parameter binding, on the WMS pick-list/put-away code path. This is the one injection point with a direct line to LOC-RISK-001, since it targets the on-hand quantity field itself. | Critical | Compounds LOC-RISK-001 directly: an attacker does not need a logic bug to corrupt QoH — a single crafted request against an already-unguarded field achieves the same outcome deliberately. | `07-risk-findings.md` §4 |
| LOC-RISK-006 | SQL injection in the "all locations for this product" summary query — a request-supplied product id is unescaped in a read query. | High | Lower business-impact than the write-path injections since it cannot directly corrupt data on its own, but a confirmed data-exfiltration vector against any table the database user can read. | `07-risk-findings.md` §4 |
| LOC-RISK-007 | SQL injection in the Cost Detail tooltip endpoint — a request-supplied id is unescaped in two read queries, plus an unvalidated request-derived dynamic column-name pair in the general audit-string branch. | High | Data-exfiltration and dynamic-column-name exposure on a low-visibility tooltip endpoint. | `07-risk-findings.md` §4 |
| LOC-RISK-008 | Concurrent-update protection is a stale-tab consistency check, not a row-level lock — two genuinely concurrent submits from the same valid session race on the same row with a silent lost-update outcome, since the only guard present anywhere is a session/tab comparison, not a serialization primitive. | High | Silent lost updates under real concurrency (double-click race, two people sharing a login). | `07-risk-findings.md` §4; LOC-RULE-011/029 |
| LOC-RISK-009 | The quantity-only merge vs. the independently-gated, non-blended cost overwrite — no configuration state guarantees a coherent, reconciled cost basis after a part-supersession event, since the quantity merge and the cost transfer are two separately-gated functions with no shared reconciliation step. | High | Financial-correctness gap: on-hand-quantity-times-weighted-average-cost is not guaranteed coherent after supersession. | `calculations.md` §10; `08-consolidation-review.md` §5 |
| LOC-RISK-010 | The kit-labeled QoH endpoint performs zero kit-component propagation despite its own name and the client-side function name that calls it — a real, filename-contradicting absence-of-behavior finding with high business-rule significance. | Medium | UI/backend mismatch; a kit-aware screen wired to a non-kit-aware endpoint. | LOC-RULE-015 |
| LOC-RISK-011 | The lost-sale factor accumulator compounds multiplicatively across repeated events for any factor other than 1, rather than applying once per event. | Medium | Demand-signal inflation for products/branches with repeated lost-sale events in the same week; not verified against a live repro. | `calculations.md` §8 |
| LOC-RISK-012 | The part-supersession merge does not re-point, cancel, or flag open Sales Order/Purchase Order lines referencing the superseded product — a cross-module gap this module's own code cannot independently confirm as a live defect or as mitigated elsewhere. | Medium | Unclear real-world behavior of in-flight orders against a just-superseded part. | `business-rules-and-validation.md` headline finding 4 |
| LOC-RISK-013 | The User-Location Tracking entity keys its branch reference by denormalized name, not a stable identifier — a branch rename silently orphans historical tracking rows (a Users-module-owned entity, flagged here as a cross-module recommendation, not fixed within this module's own scope). | Medium | Historical clock-in data orphaned by a branch rename. | `entities-and-fields.md` Known Gaps |
| LOC-RISK-014 | The two "Combine" option columns on the Product-at-Location entity have no CRM field label for either — a schema design working from field labels alone could misassign one option's meaning to the other's column. | Medium | Design-time risk for any future work not consulting the code-level citation. | `entities-and-fields.md` Known Gaps |
| LOC-RISK-015 | The Product-at-Location entity has no independent audit-trail/soft-delete/record-sharing mechanism for its 72,104 rows — the module's highest-cardinality, most business-critical data has no native history mechanism at all. | Medium | No queryable change history for the module's core data today. | `entities-and-fields.md` R1 |
| LOC-RISK-016 | The sales-history merge-and-reset in the supersession cascade is two independent, non-atomic writes — if the second statement fails or the request is interrupted between the two, the superseded product's sales-history figures are left non-zero after having already been counted once in the merge target (double-counting risk on partial failure, narrow trigger condition). | Medium | Double-counted sales history on partial-failure interruption. | LOC-RULE-019 |
| LOC-RISK-017 | The Average Days Between Sales / Average Quantity Sold formulas divide by the *configured* transaction-count limit, not the *actual* row count found — a confirmed, systematic understatement of demand/lead-time signals for any product/branch with fewer than the configured number of historical transactions, directly affecting reorder-point accuracy. | Medium | Systematically deflated reorder-point inputs for newer/slow-moving products. | `calculations.md` §2-3 |
| LOC-RISK-018 | The admin lost-sale-notification email fires unconditionally on every plain page load of the Lost Sale Log Report, not on a controlled schedule — an unbounded send-frequency/potential performance-cost risk triggered by ordinary report navigation rather than a controlled cadence. | Medium | Unbounded email-send volume tied to report navigation frequency. | `outputs.md` "The real document adjacent to the Lost Sale Log Report" |
| LOC-RISK-019 | A latent, structural fragility in the part-supersession record-creation function: the record-creation gate only guards the actual record-creation call, not the surrounding field-copy logic that runs in the same function regardless of the gate's value — no caller passing a value that would trigger this was found in any pass, so this remains theoretical, not confirmed reachable. | Low-Medium | Theoretical only; no reachable trigger confirmed. | LOC-RULE-020 |
| LOC-RISK-020 | The false-loss promotion function's wrong-temp-table-name bug — confirmed genuinely inert, zero practical impact. | Low / Informational | None — re-verified inert. | LOC-RULE-028 |
