# UOM — Risks & Open Questions

Source note: the findings below marked **[session-found]** were confirmed by this session's own direct
reads of `include/utils/commonfunctions.php` and cross-module grep — **none of them are recorded in any
existing blueprint risk-findings pass**, because no blueprint pass ever independently investigated UOM
as its own subject. They are real, code-grounded findings, but they have not gone through the same
re-verification pass (blueprint Pass 7) that every blueprint-sourced module's risk register has. Treat
severity labels here as this session's own assessment, not a blueprint-consolidated verdict. (Source:
`docs_from_blueprint/module/UOM/09-risks-and-open-questions.md`.)

## Risk Register

| ID | Finding | Severity | Impact | Source |
|---|---|---|---|---|
| UOM-RISK-001 | [session-found, Critical-shaped] SQL injection in `save_uom_group()` (`include/utils/commonfunctions.php:3873-3995`). Every field from `$param` — sourced from raw `$_REQUEST` via `uom_ajax_action.php:10` (`$param_request = $_REQUEST`) — is concatenated directly into `INSERT`/`UPDATE` SQL with no escaping and no `pquery` placeholders: `groupname`, `uomcategoryid`, all eleven `*_uomtypeid` fields, `picking_hierarchy`, and every `lbm_uom_type_qty` row's `uom_type_id`/`baseqty`/`qty` decoded from client-submitted JSON (lines 3894-3927, 3948-3976). This is a more exposed instance of the same raw-concatenation pattern already flagged repo-wide in `UpdateMassProductCriteria.php` (`PROD-VAL-029`, per Products' own risk register). Not independently verified with a proof-of-concept in this session. | Critical (session assessment, not blueprint-consolidated) | Arbitrary SQL execution via the group-save path — the single most-used UOM write operation | `commonfunctions.php:3873-3995`; dispatched from `uom_ajax_action.php` task `save_uom_group` |
| UOM-RISK-002 | [session-found] Unparameterized `$id` in `delete_uom()`'s in-use check (`commonfunctions.php:3258-3264`) — `$id` (client-submitted) is interpolated directly into a `WHERE (...= $id OR ...)` clause with no placeholder, even though the same function otherwise uses `pquery(..., array(...))` elsewhere in its own body — an inconsistency suggesting this specific clause was overlooked rather than a deliberate choice. | High (session assessment) | SQL injection in the UOM Type delete-guard query | `commonfunctions.php:3258-3264` |
| UOM-RISK-003 | [session-found] Confirmed second, independent copy of the conversion formula — `modules/Customreport/InventoryQtyByUOMTypeName.php:51-54` reimplements the quantity-conversion arithmetic inline in SQL, separate from the canonical PHP primitive (`commonfunctions.php:6137-6265+`). A formula change in one location would not propagate to the other — an active drift risk, not merely a theoretical one, since both copies already exist and diverge is only prevented by developer discipline, not any structural mechanism. | Medium (session assessment) | Inconsistent conversion results between the canonical primitive and this report's inline formula | `modules/Customreport/InventoryQtyByUOMTypeName.php:51-54`; `commonfunctions.php:6137-6265` |
| UOM-RISK-004 | [session-found] No optimistic-concurrency protection between the two UOM-price write directions — the ordinary product-edit form (base→UOM cascade) and the "Manage UOM Qty Pricing" screen (UOM→base) can both write the same underlying price fields with no shared lock or version check (`calculations.md`). A concurrent edit through each screen can silently clobber the other's write. | Medium (session assessment) | Silent data loss on concurrent price edits | `calculations.md`; `docs_from_blueprint/module/Products/05-financial-pricing-logic.md` §5.4 |
| UOM-RISK-005 | [session-found] Rounding-mode divergence is config-dependent, not a fixed invariant — whether `uom_to_base` quantity conversion rounds to a whole unit or stays fractional depends on the global `$global_qty_base_integer_sub` flag (`commonfunctions.php:6193-6224`), not on any per-product or per-UOM-type property. A rewrite needs an explicit decision here, not a silent behavior change in either direction. | Low-Medium (session assessment) | Behavior of the same conversion can differ by deployment configuration, complicating a single rewrite behavior choice | `commonfunctions.php:6193-6224` |
| UOM-RISK-006 | [open, not independently confirmed] Whether `delete_uom()`'s in-use check covers all reference points — a UOM Type can be referenced by a group via any of eleven role-specific FK slots, or by `lbm_uom_type_qty`/`lbm_uom_picking_hierarchy` rows. Whether the existing in-use guard checks all of these, or only a subset, was not traced to a specific set of guard conditions in this session. | Unconfirmed | Potential dangling references if a "still in use" type is soft-deleted via an uncovered reference path | `commonfunctions.php:3251-3264` |
| UOM-RISK-007 | [open] `lbm_applied_uom_pricing` cache-invalidation completeness — the cache is invalidated inside `save_uom_group()`, but whether every code path that could change a group's effective pricing also triggers invalidation was not exhaustively traced. A stale cache would silently serve outdated UOM-derived prices. | Unconfirmed | Stale pricing data served to consumers of the cache | `commonfunctions.php:3987-3990`; `modules/Products/uomQtyListView.php` |
| UOM-RISK-008 | [session-found] `uom_ajax_action.php`'s `save_uom_group`/`delete_uom_group` dispatch has no `isPermitted()` call in the file itself — the only permission check in the UOM area (`uom_manage.php`, page-load) only sets UI display flags and is not re-enforced server-side on the actual AJAX write endpoints. See `permissions.md` for the full finding. | Medium (session assessment) | A user who can reach the AJAX endpoint directly (bypassing the UI-gated buttons) may be able to save/delete a UOM group regardless of role | `modules/Products/uom_ajax_action.php`; `modules/Products/uom_manage.php:25-29` |
