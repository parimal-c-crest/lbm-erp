# Accounts — Business Rules & Validation

> Every rule gets a stable ID (e.g. <MOD>-RULE-001) so Stage 4's test docs can trace back to it.

Source: `docs_from_blueprint/module/Accounts/03-business-rules-and-validation.md` (Pass 2 of the
Accounts blueprint), itself derived from `blueprint/module/Accounts/02-validation-rules.md`, a full
read of `Save.php`, `Accounts.php`, `Merge.php`/`mergeAccounts.php`, `ApplyFinanceCharge.php`,
`AccountStatement.php`, the billing-cycle and past-due crons, and the SPA-code and credit-card
management files. The source catalogs 112 numbered rules (ACC-VAL-001 to ACC-VAL-112) in eight
source-file groups (Save.php; Accounts.php; Merge.php/mergeAccounts.php; ApplyFinanceCharge.php;
AccountStatement.php in five sub-groups; the billing-cycle/past-due cron; SPA-code screens;
credit-card-on-file screens). All 112 are flattened into one table below, re-IDed ACC-RULE-001
through ACC-RULE-112 (same sequence, `ACC-VAL-` → `ACC-RULE-`); Statement/Trigger/Scope/Severity are
carried over near-verbatim from the source. The source's per-rule Confidence annotations were
dropped when this document was written and live only in the deeper `02-validation-rules.md`; the
Confidence column below is reconstructed from this document by marking a rule "Inferred" wherever
its own statement or severity text already carries hedging language (unread/unclear/unconfirmed/
unverified/"flagged as"/"structural risk"/"appears") and "Confirmed" otherwise — this is a
mechanical heuristic on visible wording, not a re-verification against the deeper source. See
`## Open Questions` for the caveat this implies.

**Severity vocabulary** (carried from source): the Accounts source uses free-text severity rather
than a fixed short list, clustering around: *Hard block* (operation refused entirely), *Hard
override* (a value is unconditionally discarded/rewritten), *Hard scope-filter / hard gate* (a
record/batch/branch is silently included or excluded), *Guard* (a sub-step or optional call is
conditionally skipped), *Clamp* (a value silently floored/capped), *Not a block* (a computation
branch, auto-fill, cascade, or display rule). A smaller set of rules carry source-defined labels
outside this spectrum — *Structural risk*, *Live bug risk*, *Dead code*, *Permission gap*, *Soft/
unconfirmed enforcement* — kept verbatim because they describe a defect-adjacent condition rather
than a validation outcome (also cross-referenced in the risk register).

## 3.1 Save.php headline finding

Same pattern the SalesOrder pilot found in its own `Save.php`: this file is almost entirely
save-orchestration/field-cascade/cross-module-sync code, not field-level validation — no true hard
block exists anywhere in it. No required-field enforcement was found for any header field despite
several being documented as required elsewhere. ACC-RULE-010 is a genuine hard override that
silently discards a submitted field value on every edit once a business condition is met.

## 3.2 Accounts.php headline finding

The entity save hook contains zero hard validation — every branch is a conditional default-fill or
bookkeeping side-effect, never an abort. The account-authentication function builds its query by
direct string concatenation with no parameterization or visible hashing (security item, not a
business-rule finding per se). The two statement-generation entry points (full Statement view vs.
Quick Statement view) are ~700-line near-duplicated implementations with one confirmed behavioral
drift (ACC-RULE-025).

## 3.3 Merge.php / mergeAccounts.php headline finding

Despite its name, `Merge.php` is not the account-record dedupe/merge feature — it is a legacy Word
mail-merge template exporter. The real account-merge/dedupe logic lives in `mergeAccounts.php`,
delegated to two functions not read in this pass; this file is an orchestration/guard wrapper, not
the merge algorithm itself.

## 3.4 ApplyFinanceCharge.php headline finding

The manual/batch finance-charge posting engine contains genuine financial computation, not just
save-orchestration. The ledger-record creation forks into two different code paths depending on the
caller (raw direct insert vs. normal entity save flow), so validation/side-effects on the normal
save path are bypassed entirely for one of the two paths (ACC-RULE-047).

## 3.5 AccountStatement.php headline finding

The statement-rendering/aging engine has almost no true "reject the save" validation (it's a read/
report path) but a very large surface of silent business-rule branching that determines what a
statement shows and how balances are computed — several with direct financial-correctness
implications (e.g. ACC-RULE-058's blanket "non-charge transactions are always fully paid on the
statement" override, and ACC-RULE-061's Statement-Sequence setting being silently ignored for
Balance-Forward accounts).

## 3.6 Billing-cycle & past-due cron headline finding

`BillingCycleCron.php` is the production driver for everything in §3.5's aging/finance-charge
subsections — it rebuilds statement working data once, then loops every non-deleted account applying
a 3-way branch (Finance-Charge-by-Job / not-by-Job / Manual) determining whether finance charges
post and how billing-cycle past-due is recomputed a second time.

## 3.8 Credit-card-on-file headline finding

Both the credit-card management screen and the credit-card lookup endpoint directly query/insert/
delete a legacy credit-card-on-file table with no existence check, no try/catch, and no graceful
fallback — and an earlier blueprint pass confirmed that table is absent from the live dev database
(ACC-RULE-109), a live bug risk rather than a business-rule finding.

## Open Questions

- **No confirmed server-side required-field enforcement anywhere in this module** — Save.php and
  Accounts.php were both searched for header-field required-ness (Master Account Name, Master
  Account Number, Parent Account, etc.) and neither shows any; enforcement may be client-side only,
  or may not exist at all. Needs SME confirmation.
- **The account-merge algorithm's own internals were not read** — `mergeAccounts.php` (ACC-RULE-034
  to 037) delegates the actual field-reassignment logic (what happens to each child entity type —
  Contacts, Jobs, Sales Orders, Credit Cards, SPA Codes — when an account is merged away) to two
  functions outside this pass's read scope. Not captured anywhere in this rule catalog.
- **The missing credit-card-on-file table (ACC-RULE-109) needs DBA/human confirmation** — an earlier
  blueprint pass found the legacy table absent from the live dev database; unclear whether it exists
  under a different name, or whether these code paths are simply un-migrated in favor of the
  parallel PCI-vault-tokenized gateway mechanism.
- **Several functions called from the save flow were never read in full** and may contain additional
  validation not captured in this catalog: the tax-authority-table lookup (ACC-RULE-013), the
  sales-group update (ACC-RULE-014), the account-rename propagation (ACC-RULE-015), the
  phone-to-contact reconciliation (ACC-RULE-019), and the account-duplicate-blocking caller code
  (ACC-RULE-022).
- **Whether the FIFO balance-forward credit-application algorithm (ACC-RULE-071) has any live caller**
  outside this pass's read scope — all call sites found so far are commented out, so it currently
  reads as dead code, but this wasn't traced exhaustively.
- **The two uncatalogued credit-card fallback fields (ACC-RULE-112)** have no field-definition row
  and aren't present in the module's field catalog; their origin/purpose is unconfirmed, and the
  fallback path they support is itself believed unreachable per ACC-RULE-109.
- **A dedicated legacy custom-field write function referenced near Save.php** appears to be dead code
  (its only call site is commented out) and writes to a superseded legacy table rather than the live
  custom-fields mechanism — flagged in §3.1 but not assigned its own rule ID.
- **Twelve systemic bug/defect candidates were surfaced incidentally while cataloging these rules**
  (per the source's §3.9 rule-catalog notes), including the missing credit-card table
  (ACC-RULE-109), the mislabeled `Merge.php` (§3.3), two independent finance-charge-suppression
  implementations (ACC-RULE-044/076), three independent reimplementations of payment-term
  date-boundary parsing (ACC-RULE-066/068/095), and the credit-card 50-count off-by-one
  (ACC-RULE-110) — tracked in the risk register (Known Risks), not restated here.
- **Confidence-column caveat**: the source document this file was built from (
  `docs_from_blueprint/module/Accounts/03-business-rules-and-validation.md`) explicitly states that

  in the deeper `blueprint/module/Accounts/02-validation-rules.md`. The Confidence column above was
