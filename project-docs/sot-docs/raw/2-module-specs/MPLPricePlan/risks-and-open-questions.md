# MPLPricePlan — Risks & Open Questions

Source: `docs_from_blueprint/module/MPLPricePlan/09-risks-and-open-questions.md`, itself consolidated
from `blueprint/module/MPLPricePlan/07-risk-findings.md` (severity re-verification pass) and
`blueprint/module/MPLPricePlan/08-consolidation-review.md` (master rollup pass, verdict "reviewed", no
blocking corrections needed). **This is the widest confirmed injection surface, by Critical-finding
count, of any module blueprinted in this series to date** — the four Critical findings below are the
highest-priority input to any new implementation's design.

## Risk Register

| ID | Finding | Severity | Impact | Source |
|---|---|---|---|---|
| MPL-RISK-001 | A standalone rule-delete script (`DeleteRule.php`) deletes from a live table belonging to a completely unrelated module (Pricebooklevel800), via an unescaped, unbound caller-supplied id. Two independently severe components: (a) a wrong-table write — even a perfectly-formed, non-malicious id reaching this endpoint deletes a row from a table with no relationship to MPLPricePlan at all, a correctness defect independent of the injection; (b) an unmitigated SQL injection on top of it. Reachable by any authenticated user via direct URL construction, no permission check beyond session authentication, no caller found anywhere in this module's own client-side code or the wider source repository (dead-code-from-the-UI's-perspective, but live-reachable by direct URL). Even a fix that "merely" adds parameterization without also fixing the table name would leave the wrong-table-deletion defect fully intact. | Critical | Corrupts an unrelated module's live production data; no authorization boundary of any kind gates this action. See `permissions.md` for the authorization-gap treatment. | `blueprint/module/MPLPricePlan/07-risk-findings.md` §1; MPL-RULE-019 |
| MPL-RISK-002 | The plan-save flow's rule-scope block — 8 raw-concatenated SQL statements, reachable via the module's own everyday save action. Not a rare or deliberately-triggered path; every one of the 8 statements is reachable by any user who can open a plan's edit screen and submit the Rule Section form. | Critical | Any user who can open a plan's edit screen can potentially inject SQL through the module's own everyday save action. | `blueprint/module/MPLPricePlan/07-risk-findings.md` §2.1; MPL-RULE-007–012 |
| MPL-RISK-003 | The ajax business-logic layer's 6 further raw-concatenated injection points, including the "copy to other locations" fan-out — the single widest blast-radius finding in this module, since it runs in a loop across every tenant location whenever the location-uniformity toggle defaults to off: a single malicious plan-id value in one grid-save request is replayed — and could inject — once per tenant location in a single request, not once. | Critical | Widest blast radius of any single injection point in this module — one malicious request can inject once per tenant location. | `blueprint/module/MPLPricePlan/07-risk-findings.md` §2.2; MPL-RULE-022, 024–029 |
| MPL-RISK-004 | The Rule Section's two read-path injections — reachable on every single visit to a plan's edit screen, not a specifically-triggered action; this fires through ordinary navigation. | Critical | Every ordinary visit to a plan's edit screen executes an injectable read query. | `blueprint/module/MPLPricePlan/07-risk-findings.md` §2.3; MPL-RULE-020–021 |
| MPL-RISK-005 | The plan CSV-export feature is a non-functional stub — not a security finding, but a confirmed functional defect on a feature every other module in this series has working. | High | Export feature does not work; user-visible failure mode not confirmed. | `docs_from_blueprint/module/MPLPricePlan/06-outputs.md`; MPL-RULE-004 |
| MPL-RISK-006 | A live, unguarded divide-by-zero in the `GP%` pricing formula at `value = 100` — no currently-triggering live row on the source blueprint's dev snapshot, but one save-time typo away from firing, and the plan-save flow performs no numeric-range validation on this field. | High | Would produce an infinite/undefined price value flowing into the sales-order line-item pricing UI, undetected by the existing zero-price-suppression check. | `docs_from_blueprint/module/MPLPricePlan/05-financial-pricing-logic.md` §5.4 |
| MPL-RISK-007 | The rule-delete operation's missing ownership/scope check — any rule id can be soft-deleted regardless of which plan's edit screen the request nominally originates from, and the deletion does not cascade to the rule's own scope-junction rows, leaving them orphaned. | High | Orphaned scope-junction rows accumulate; a rule belonging to one plan could in principle be deleted while editing a different plan's Rule Section. | `docs_from_blueprint/module/MPLPricePlan/04-status-workflow.md` §4.2 |
| MPL-RISK-008 | The Rule sub-entity has a real, UI-maintained write path and — per every pass that traced it — zero read consumers anywhere in the live pricing-computation path. Not a security finding, but a substantial "built, never wired up" architecture gap: a merchandiser using the Rule Section today is authoring data that has no effect on any product's actual sale price. | Medium | A merchandiser can believe they are configuring pricing rules that have zero actual effect on any sale — a silent, undetectable-to-the-user gap. | `docs_from_blueprint/module/MPLPricePlan/02-entities-and-fields.md` §2 entity 4; `09-risks-and-open-questions.md` §9.1 finding 8 |
| MPL-RISK-009 | The location-uniformity toggle's default-off (uniform-copy-to-all-locations) behavior means editing one location's pricing grid silently overwrites every other tenant location's grid for the same plan by default — not a bug in the narrow sense (the code does exactly what it is built to do), but a genuine footgun risk given the toggle's default state, with a blast radius comparable in scale to MPL-RISK-003 even without any malicious input involved. | Medium | Any ordinary grid edit can silently overwrite every other tenant location's pricing for that plan. | `docs_from_blueprint/module/MPLPricePlan/04-status-workflow.md` §4.3 |
| MPL-RISK-010 | An unrecognized `formula` string or a computed sales price of exactly `0` both silently drop a line from pricing with no error surfaced anywhere in the traced path, and the plan-save flow performs no allow-list validation on the `formula` field at all — a save-time typo produces a silently-unpriced product, discoverable only by a merchandiser noticing a specific product has no price at a specific pricing level, not by any error or log. | Medium | Products can silently have no price at a given pricing level with no error surfaced anywhere. | `docs_from_blueprint/module/MPLPricePlan/05-financial-pricing-logic.md` §5.3.2/§5.3.5 |
| MPL-RISK-011 | The ListView's sort-by field declaration lists two placeholder column names that don't exist on the plan header table — sorting the list view by either is a likely-broken feature. | Medium | Low practical impact (a cosmetic/UX defect, not data-integrity), grouped here for completeness. | `docs_from_blueprint/module/MPLPricePlan/03-business-rules-and-validation.md`; MPL-RULE-003 |
| MPL-RISK-012 | The standard delete-action slot contains no delete logic at all — not itself a defect (the real delete path works and is guarded, MPL-RISK-001's contrast point), but a structural deviation from every prior module's own delete-action convention in this series. | Low/Informational | None directly — informational, flags a structural inconsistency for reviewers. | `docs_from_blueprint/module/MPLPricePlan/03-business-rules-and-validation.md`; MPL-RULE-018 |
| MPL-RISK-013 | A base64-decoded error-message parameter in the list view — informational only, display-path only, not concatenated into SQL or evaluated as code. | Low/Informational | None confirmed. | `blueprint/module/MPLPricePlan/07-risk-findings.md` (Low/Informational group) |
| MPL-RISK-014 | A shared product-save helper's own raw-concatenated assignment-write statements — technically outside this module's own files, since it belongs to the Products capability/shared-utility layer, but load-bearing for the data this module's own pricing-consumption logic depends on. | Low/Informational | A MPLPricePlan-focused rewrite would need to fix it regardless of which module "owns" the fix. | `blueprint/module/MPLPricePlan/07-risk-findings.md` (Low/Informational group) |

## The single highest-priority unresolved question

Whether the Rule sub-entity's confirmed lack of a pricing-engine consumer (MPL-RISK-008) reflects a
removed feature, a planned-but-never-built one, or a genuine gap in the source blueprint's own search
method. This is "resolved enough to act on" only in the narrow sense that "no consumer exists in the code
today" is itself a confirmed, code-level fact (independently re-confirmed by five separate passes in the
source blueprint with no contradiction across any of them) — but the broader product question (was this
feature meant to be finished, and should it be) remains open and is explicitly deferred to a human,
subject-matter-expert decision rather than silently defaulted either way. This mirrors the
`DeleteRule.php` wrong-table finding (MPL-RISK-001) in being the module's other candidate for "single
highest-priority" status — the two are kept as co-equal top-priority items rather than artificially
ranked against each other, since one is a security/data-integrity defect requiring immediate
legacy-system remediation and the other is a product-scoping decision blocking full build-phase scoping;
they are not commensurable on the same scale.
