# ProductTracking — Cross-Module & Integration Touchpoints

Part of the ProductTracking tech-agnostic module spec. Source:
`blueprint/module/ProductTracking/06-cross-module-integrations.md` (Doc1 Pass 6), ultimately derived
from `blueprint/module/ProductTracking/`.

**This is ProductTracking's standout area.** ProductTracking is structurally inverted relative to a
typical business-entity module: it is not an independently-authored entity other modules reference — it
is a **write-target for QoH-affecting events across a very wide span of the application**. Its writer
set spans at least **11 distinct modules plus 2 external-facing webservice endpoints plus a family of
standalone report/utility scripts** — the widest confirmed writer fan-in of any module blueprinted in
this series so far (Pass 6 §1.0).

## 7.1 Related-capability boundaries

| Capability | What crosses the boundary | Direction | Notes |
|---|---|---|---|
| **A shared writer function, reused by ≥5 confirmed callers** | A thin, shared wrapper around direct entity instantiation: resolves a WAC lookup, maps a caller-supplied data array directly onto the entity's field map, and saves. Confirmed callers include the mobile-scanner webservice's store-transfer-cancellation flow (§7.2), WMS reconciliation, and a generic order-entry/manufacturing QoH bookkeeping path (whose `change_type = 'Manufacturing'` value does not appear in the module's own live data distribution — real code, unconfirmed live usage). A fourth confirmed call site exists but both of its own call statements are commented out — dead code on this branch, not a live writer. | Caller module → ProductTracking, write-only | This is the module's closest analog to a single shared write path, except multiple, independent modules all funnel through the same shared function rather than each writing directly. |
| **Direct entity instantiation — the wider, module-by-module writer fan-in** | Confirmed by a repo-wide search (26 non-blueprint files). Spot-read/context-read sites confirm: a SalesOrder-line-delete inventory-rollback write (`change_type = 'Sales Order'`); a Store-Transfer partial-cancellation write, direct (not via the shared function); SalesOrder's own finalize/return/QoH-update paths (independently confirmed as a ProductTracking writer, distinct from its role as SearchLineItem's own writer); PurchaseOrder's receiving/RGN/cancellation paths; Receiving and Receiving-Store-Transfer save flows; StoreTransfer's own entity save; Pending-store-transfer receipt flows; **9 distinct Products-module files** (the widest single-module writer surface found — serial/lot-number and physical-inventory-count sub-flows); bulk product creation; the Quick-Edit UI path; the Product-Cut-flag origin module; Location-side direct QoH-edit ajax endpoints and kit-QoH updates; PhysicalInventory's reconciliation flow; bulk product import; and a family of standalone scan-inventory/manual-count custom-report scripts plus top-level utility/data-migration scripts and DB-utility/admin scripts outside any module directory. | Each caller module → ProductTracking, write-only | Only a subset of these 26 files were spot-read or context-read in the blueprint; the remainder are named as real, grep-confirmed reference points, not asserted-safe or asserted-unsafe individually. |
| **A 12-report custom-report family** | Reads ProductTracking's audit-log data without writing to it. The sheer number of named custom reports built on this table (12, more than any other single consumer category found in the blueprint) confirms the module's data has real, ongoing operational/reporting value beyond its own thin UI. | ProductTracking → report family, read-only | None of the 12 report files were full-read in the blueprint — named as confirmed reference points. |
| **PurchaseOrder's own receiving-variance PDF report** | Produces a PDF receiving-variance report that references ProductTracking's data as one input among others — the PDF itself is generated by PurchaseOrder's own code, not by ProductTracking. | ProductTracking → PurchaseOrder's own report, read-only | Does not contradict ProductTracking's own finding that it has no PDF output of its own (this module's outputs documentation). |

## 7.2 External system boundaries

| Integration | What crosses the boundary | Direction | Notes |
|---|---|---|---|
| **Mobile-scanner webservice** | Writes into ProductTracking via the shared writer function, fed by request-payload values sourced directly from the external scanner device's own webservice request, not from an internal session-scoped lookup. | External mobile-scanner device → ProductTracking, write-only | **This module's one confirmed externally-reachable write path.** A materially different reachability profile from every other writer above (all of which are reached only through the application's own session-authenticated web UI): a compromised or malicious scanner-device credential could reach the shared writer function's own unescaped location/product-number splice directly, without needing a web-session login at all. |
| **QuickBooks** | The entity's own save hook conditionally calls a QuickBooks cost-push function when the writer sets `push_to_qb = 'Yes'`. | ProductTracking → QuickBooks, write (conditional, at save time) | Unlike some sibling modules (which have zero direct QuickBooks references inside their own files), ProductTracking references the QuickBooks integration directly from its own entity class — a real, if narrow, external-integration touchpoint owned by this module itself, not merely a data source for someone else's integration. |

**Direct summary of the external-integration question**: ProductTracking is both a genuine **write
target** for one external-facing consumer (the mobile-scanner webservice — a materially riskier
reachability profile than any of its internal writers) and a genuine **integration owner** in its own
right (the QuickBooks push), a combination not found in every module of this series.

## 7.3 Cross-module/integration open items

- **Whether the shared writer function's reachability from the mobile-scanner webservice is gated by any
  authentication/authorization layer the blueprint did not trace** — the scanner webservice's own
  request-authentication scaffolding was not read; this is material to the severity of the SQL-injection
  finding reachable through this path (see this module's risks-and-open-questions documentation).
- **Whether any of the 22 grep-confirmed-but-not-full-read writer files pass request-derived values into
  the entity's field map the way the mobile-scanner webservice and the inline-edit endpoint do** — not
  confirmed for any of them; each is currently treated as an unread reference point, not asserted safe or
  unsafe. A full-read sweep of all ≥26 writer files would be needed to close this out completely.
- **The `change_type = 'Manufacturing'` value** found in the shared writer function's callers does not
  appear in the module's own live `change_type` distribution on the blueprint's dev tenant — real code
  path, unconfirmed live usage.
- **PurchaseOrder's receiving-variance PDF report's own use of ProductTracking data** — not read in the
  blueprint; whether it recomputes or merely displays this module's own cost/QoH figures is unconfirmed.
