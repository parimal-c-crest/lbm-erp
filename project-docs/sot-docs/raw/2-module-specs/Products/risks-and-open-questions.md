# Products — Risks & Open Questions

Source: `docs_from_blueprint/module/Products/09-risks-and-open-questions.md` (itself consolidated from
`blueprint/module/Products/07-risk-findings.md` and `blueprint/module/Products/08-consolidation-review.md`).

**This module carries the strongest security-remediation urgency of any module blueprinted in this series
to date** — 11 confirmed, directly exploitable SQL injections across 11 files, 5 of them Critical (the
highest raw Critical count of any module in the series), one of them (PROD-RISK-002) reachable from the
single most ordinary, highest-traffic save action in the module: an everyday product edit with a changed
cost field under Global WAC mode. Every entry below preserves that urgency framing verbatim rather than
softening it into a generic "known issue." Items 1–5 (the five confirmed Critical SQL injections) need
legacy-system remediation **now, independent of any rewrite timeline** — they are live in production
today.

## Risk Register

| ID | Finding | Severity | Impact | Source |
|---|---|---|---|---|
| PROD-RISK-001 | SQL injection via arbitrary column name *and* value in the mass-update apply path (`UpdateMassProductCriteria.php`) — the mass-updatable field list is built by matching *any* request key against a naming pattern, so a crafted request key becomes an unwhitelisted column-name token for any field not on the enumerated list; every field's value (enumerated or not) is separately confirmed unescaped. The richest single injection surface found in this blueprint series to date. | Critical | Both column-name *and* value control in the same statement. Mitigation: mass-update field allow-list enforced server-side as a domain invariant (never merely a UI restriction) — any field key not on the allow-list is rejected before any query is built; every value always parameterized, never concatenated. | Doc1 §07 §1 Finding 3 |
| PROD-RISK-002 | SQL injection inside the Product entity's own core save hook's Global-WAC recalculation block (`Products.php::save_module()`) — a location identifier is spliced unescaped into two query fragments inside the save hook itself. **Unlike every other Critical finding in this module, this requires no admin screen, no special permission, and no unusual workflow — it is reachable by the same save action every warehouse/receiving user performs routinely.** Explicitly singled out as "the single most routine, highest-traffic reachability of any Critical finding yet documented" across the whole blueprint-consolidation series to date. **Highest-reachability finding in this register.** | Critical | Mitigation: the save operation has no code path that reaches the database with any request-derived value not already validated/typed by the aggregate boundary — location resolution for the Global-WAC recompute uses a typed, foreign-key-validated identifier, never a raw request string. Given the reachability, this is the first security-regression test a new implementation's build sequence should write. | Doc1 §07 §2c #10; §08 §6 |
| PROD-RISK-003 | SQL injection via an unwhitelisted column name in the barcode-ambiguity "resolve" write-back (`saveBarcode.php`) — an earlier analysis pass had flagged this write-back as unlocated; the re-verification sweep found it accepts a request-supplied barcode-type value unquoted as a raw column name in both an UPDATE and a DELETE statement; the paired value is itself unvalidated, chaining off an already-documented unvalidated session-write input — a two-hop injection chain. | Critical | Mitigation: the vulnerable feature is eliminated entirely — the new design's real barcode-uniqueness constraint (PROD-RISK-017) means there is no after-the-fact ambiguity to detect or resolve, so there is no "clear this ambiguous field" endpoint left for an injection to target — the strongest form of closure available. | Doc1 §07 §2c #1 |
| PROD-RISK-004 | SQL injection via unwhitelisted column names in both rule-engines' inline-edit endpoints (`SaveAutoUpdatePriceFieldsValues.php` and `SaveAutoUpdateSublineValues.php`) — each accepts an arbitrary field name as a raw column token; the value in each case is correctly parameterized, but the column-name token is not validated against any whitelist. | Critical | Mitigation: both endpoints' successors resolve the target field against an explicit allow-list of the rule table's real editable columns — the field name is never used as a raw column token. | Doc1 §07 §2c #2-3 |
| PROD-RISK-005 | SQL injection with no quoting or bind mechanism at all in the lot-number-delete endpoint (`deleteTempLotNumber.php`) — an id value is concatenated **unquoted and with no bind array of any kind** (not even an empty one) into both a read and a delete statement — even a numeric-looking payload with a trailing SQL fragment is not contained by any quote character at all. | Critical | Mitigation: the id is always a typed integer, bound as a real parameter — the "not even an empty bind array" pattern is structurally unavailable, since the new data-access layer has no raw-execute path for business-logic code at all. | Doc1 §07 §2c #4 |
| PROD-RISK-006 | Quote-breakout SQL injection in three rule-delete endpoints (AUPF rule delete, Auto-Update-Subline rule delete, Product Defaults Rule delete) — a rule id is unescaped in each of three otherwise-independent delete statements. | High | Mitigation: every successor endpoint parameterizes the id. | Doc1 §07 §2c #5-7 |
| PROD-RISK-007 | Read-path SQL injection in two files (`undefinedProduct.php`, `IsPartTaxed.php`) — a product-group id and a product/account id pair are each unescaped in select statements; the account-tax-driven taxability check is the one finding confirmed reachable from **ordinary, non-admin sales-order line-item entry** rather than an admin-scoped screen — the highest-traffic read-path injection found in this module. | High | Mitigation: both endpoints' successors parameterize every identifier; the taxability-check endpoint is singled out for its own dedicated regression test given its ordinary-traffic reachability. | Doc1 §07 §2c #8-9 |
| PROD-RISK-008 | The mass-update apply path has no count-confirmation, dry-run, or batch-size cap — a broad "match every classification" scope combined with a wide field selection can already mass-update every non-deleted product/location row in the system in one honest, non-adversarial operator action gone wrong, entirely independent of the SQL-injection findings above. | High | Mitigation: a new, explicit application-service gate requires a server-computed affected-row-count preview step before execution, with a confirmation token tying the preview to the actual execute call. | Doc1 §02 cross-cutting finding; §07 §3 item 8 |
| PROD-RISK-009 | The Auto-Update-Subline "blank-scope mass-rewrite" claim does not reproduce as originally characterized — **downgraded from an earlier Critical rating**: a hard database-query filter already excludes blank-scoped rules on both the manual-apply and scheduled-cron entry points before the originally-flagged no-op guard is ever reached, so today's practical worst case is bounded to one classification, not the entire catalog. The design-level fragility (today's safety being an accident of one query filter in one file staying in sync with a second, independently-maintained query filter in a sibling file) is real and worth closing properly, even though it is not a currently-live exploit. | Medium (downgraded from Critical) | Mitigation: a real, save-time non-empty-scope domain invariant on both rule types, not reliance on an incidental downstream filter. | Doc1 §07 §1 Finding 1; §08 §3.1 |
| PROD-RISK-010 | The Global-WAC formula's hardcoded zero term — the "blend the edited location's existing inventory at its own prior cost" half of a textbook weighted-average formula never executes today; every other location's existing quantity is additionally revalued at the newly-entered cost rather than its own individually-tracked cost. Original intent (deliberate full-revaluation design, or a latent bug) was never confirmed from the code alone. | Medium | Mitigation: a corrected weighted-average formula, explicitly flagged for subject-matter-expert sign-off given the direct cost/COGS correctness stakes. | Doc1 §04 §9 Open Question 1; §07 §3 item 10 |
| PROD-RISK-011 | The Gross-Profit-calculation ajax endpoint's GP half is unconditionally dead code (`getSellAndGpPrice.php`) — an unconditional exit halts execution before the GP-computation half runs, plus a second, independent bug (the result variable is never populated even if that exit were removed). GP itself is not dead system-wide — two other live formulas exist and are actively used elsewhere. | Medium | Mitigation: not ported; fully subsumed by explicitly calling the price-resolution service, then the GP-calculation service. | Doc1 §07 §3 item 11 (Pass 4 §5) |
| PROD-RISK-012 | The supersession trigger's undefined-variable bug (`SaveSupercession.php`) — a guard variable is referenced but never assigned anywhere in the file, making the intended "only merge if the old classification is genuinely non-blank" condition a permanent no-op; does not appear to change net behavior since the sibling condition is correctly derived, but is dead/broken logic. | Medium | Mitigation: fixed, not ported — the new command has no equivalent no-op-prone guard to accidentally disable. | Doc1 §07 §3 item 12 |
| PROD-RISK-013 | The ZPL/EPL label-printing file has two inconsistent PrintNode delivery mechanisms (`PrintZplLabel.php`) — some branches call the shared delivery function in-process; others self-originate an HTTP request into a separate top-level dispatcher script. Both reach the same account/printer but are not the same code path — a maintainability/consistency risk, not a security risk. | Medium | Mitigation: unified into one shared delivery service in the new design. | Doc1 §07 §3 item 13 |
| PROD-RISK-014 | A generic duplicate-lookup helper's (`checkDuplicateValue()`) hardcoded literal for one specific classification table — the match condition is hardcoded to one specific fixed value regardless of what is actually being checked, meaning a genuine duplicate for any *other* value could silently slip past the intended uniqueness guard in the vendor-linecode master-data editor. Never confirmed intentional or accidental. | Low-Medium | Mitigation: fixed — the duplicate-check always matches the actually-submitted value. | Doc1 (source of PROD-RULE-065) |
| PROD-RISK-015 | The Product-header supersession pair's six orphaned live rows — an exhaustive negative search (the supersession trigger, both mass-update mechanisms, CSV import) found no write site anywhere for these two Product-header fields, yet six live rows carry real data — most plausibly a one-time data-migration artifact or a since-removed code path. A schema design that treats these fields as live-maintained without investigating this gap would be building on orphaned data. | Low-Medium | Mitigation: redefined as a read-only, event-synced projection of Location's own authoritative transition; migration must investigate the six rows' origin before cutover. | Doc1 §03 §2.2 |
| PROD-RISK-016 | The base→UOM and UOM(base-row)→base pricing-write directions have no confirmed coordination — both write directions exist, and no shared lock or version check was found in either function body, a genuine concurrent-edit data-integrity risk. | Low-Medium | Mitigation: real optimistic-concurrency protection added to the shared write path — see this module's pricing/calculation documentation §5.4. | Doc1 §04 §9 Open Question 2 |
| PROD-RISK-017 | Barcode uniqueness remains confirmed unenforced at save time in the legacy system, compounded by the discovery that the "resolve" write-back is itself SQL-injectable (PROD-RISK-003) — duplicates are both creatable without a gate and "resolved" through an injectable endpoint. | Low-Medium | Mitigation: closed by construction via the new save-time uniqueness invariant. | Doc1 §02 cross-cutting finding |
| PROD-RISK-018 | Lot-number uniqueness remains confirmed asymmetric with serial numbers, compounded by the lot-number-delete endpoint (PROD-RISK-005) being separately SQL-injectable — the asymmetry itself is confirmed correct business logic (see this module's entities-and-fields documentation, requirement R4); the injection is closed structurally alongside every other SQL-injection finding. | Low-Medium | Mitigation: injection closed structurally alongside every other SQL-injection finding; the asymmetry itself preserved as correct business logic, not "fixed." | Doc1 (source of PROD-RULE-058) |
| PROD-RISK-019 | Two advisory-only validation functions (`checkCaseFullForReturn()`, `checkSNExistInCase()`) leave enforcement entirely to an unread/unconfirmed caller — a case-fullness-for-return check and a case-barcode-quantity-consistency check both compute a real result but neither this module nor any later analysis pass confirmed whether their caller actually acts on that result, or silently ignores it. | Low-Medium | Mitigation: promoted to real, enforced domain invariants in the new design — an over-return or an inconsistent quantity edit is rejected outright, not merely computed and handed off. | Doc1 (source of PROD-RULE-063/064) |
| PROD-RISK-020 | The Price-Code-Book/Rank-Group dual-write question is resolved-absent, not open — Products' own inline write path into the two mapping tables is confirmed 100% unreachable dead code; the only live writer today is the two dedicated modules' own management screens. No race exists today. | Low/Informational | A documentation correction, not a code risk. | Doc1 §06 §1.6 OQ4; §07 Finding 2 |
| PROD-RISK-021 | An orphaned MPL backup table — a full timestamped structural duplicate of the live MPL pricing table, most likely a one-time pre-migration/pre-import safety snapshot, still present in the live system with tens of thousands of rows, not read or written by any traced code path. | Low/Informational | Safe to archive outside the application, but flagged for migration planning so it isn't mistaken for a second live MPL source. | Doc1 §01 Schema Drift #1; §07 §3 item 15 |
| PROD-RISK-022 | A second, extension-level soft-delete-shaped column (`vtiger_productcf.deleted`), re-confirmed as the standard legacy extension-table pattern, not an anomaly. | Low/Informational | No further action needed. | Doc1 §01 Schema Drift #2; §07 §3 item 16 |
