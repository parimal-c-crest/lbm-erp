# SearchLineItem — Business Rules & Validation

> Every rule gets a stable ID (e.g. <MOD>-RULE-001) so Stage 4's test docs can trace back to it.

Source: `docs_from_blueprint/module/SearchLineItem/03-business-rules-and-validation.md` (rule IDs
renumbered `SLI-VAL-###` → `SLI-RULE-###`, preserving order/grouping), cross-checked against
`blueprint/module/SearchLineItem/02-validation-rules.md` for legacy file:line citations.

The blueprint catalogs **19 numbered business/validation rules** — at the low end of the expected range
for this series, consistent with the module's own headline finding that its user-facing data-entry
validation is genuinely close to nonexistent, since the module's own EditView/Save.php scaffolding is
vestigial. **Headline finding — two confirmed, unmitigated SQL injections** (SLI-RULE-014, SLI-RULE-019).

**Severity legend**: *Hard block* = the operation is refused/rejected entirely; *Guard* = a sub-step or
side effect is conditionally skipped, not the whole operation; *Not a block* = documents an
absence-of-guard finding, a computation branch, or a structural observation rather than a validation per
se; *Critical (security)* = a confirmed, unmitigated SQL injection.

**Confidence legend**: Confirmed (explicit source, code-cited) / Inferred (deduced, needs verification).

| SLI-RULE-007 | Once the presence check passes, the soft-delete write runs unconditionally — no existence check on the record id, no check for any related/referencing data, no permission check performed in this file itself. | Every delete with a non-empty record id | Search Line Item row (soft-delete) | None are hard blocks beyond the presence check | Confirmed |
| SLI-RULE-008 | The record id is passed as a bound query parameter — safe from SQL injection via parameterization, but there is no numeric/format validation of the value before use; a non-numeric or malformed id simply matches zero rows silently. | Every delete | Search Line Item row id | Not a block — silent no-op on non-matching id | Confirmed |
| SLI-RULE-009 | The field-save logic runs only if the record id is non-empty; otherwise the endpoint returns a silent-failure response and nothing is written or queried. | Every inline field edit | Search Line Item record id | Hard block (silent-failure response, not a visible error page) | Confirmed |
| SLI-RULE-010 | The submitted field value is assigned directly to the entity's field map with no allow-list of editable field names, no type/format check, and no bounds check — any field name/value pair the caller supplies is accepted and saved, the same mass-assignment-shaped gap found across this series' equivalent endpoints. | Every inline field edit | Any field editable via this endpoint | None are hard blocks | Confirmed |
| SLI-RULE-011 | Editing Extended Product Cost recomputes Margin Dollars/Margin Percentage as `(extended sell price − extended cost)` and `(extended sell price − extended cost) / extended sell price × 100`, with **no check that extended sell price is non-zero** before the division — a live division-by-zero/data-corruption risk, confirmed exposed on real data (38 of 7,074 rows have extended sell price at zero/unset at blueprint time). | Inline edit of Extended Product Cost on a line where Extended Sellprice is zero or unset | Margin Dollars, Margin Percentage | Not a block — a live divide-by-zero/data-corruption risk | Confirmed |
| SLI-RULE-012 | Editing Extended Original Product Cost computes `new original cost = extended original cost / shipped quantity`, with **no check that shipped quantity is non-zero** before the division, and this write runs **unconditionally and immediately** — before the entity's normal save call — bypassing the entity save layer entirely for this one column; confirmed exposed on real data (31 of 7,074 rows have shipped quantity at zero/unset). | Inline edit of Extended Original Product Cost, especially on a line where Shipped Qty is zero or unset | Original Product Cost | Not a block — divide-by-zero risk plus an unconditional pre-save side-effect write with no transactional tie to the entity save that follows it | Confirmed |
| SLI-RULE-013 | Neither of the two divide-prone branches above validates that the submitted field value is actually numeric before casting — a non-numeric submitted value silently casts to zero, producing a distorted margin or a zero cost rather than being rejected. | Inline edit of either field with a non-numeric value | Margin Dollars/Percentage, Original Product Cost | Not a block — silent coercion to zero rather than rejection | Confirmed |
| SLI-RULE-014 | The alert-dismiss action is gated only on the submitted id-list being non-empty and `trim()`'d — no numeric format validation, no escaping, and **no parameterization at all** before the value is interpolated directly into an `UPDATE ... WHERE sliid IN (...)` statement and executed with no bound-parameter array — a fully unmitigated SQL injection reachable by any authenticated user who can call this ajax endpoint, with no permission check inside the file beyond session authentication. | Every "Remove Alert"/"Action Taken, Remove Selected" click on the supersede/return worklist | Superseded/Return Alert Flag, and — given the injection sits in an `UPDATE` statement with attacker-controlled `WHERE` — potentially any row/table reachable from this database connection | **Critical (security) — confirmed SQL injection, no mitigation** | Confirmed |
| SLI-RULE-015 | No check exists that the submitted id(s) actually have the Superseded/Return Alert Flag currently set before it is reset — any id, flagged or not, can be targeted; this is a logical-scope gap independent of the injection above (i.e. still present even in a hypothetically parameterized rewrite of this query). | Every alert-dismiss action | Superseded/Return Alert Flag | Not a block — no state-precondition check | Confirmed |
| SLI-RULE-016 | The report-generation query itself (the worklist's own read query) takes no request input at all — it is a fixed, fully static filter — so the read side of this workflow carries no injection risk; the vulnerability is confined entirely to the write side (SLI-RULE-014). | Every worklist render | N/A — confirms absence of a second injection point | N/A | Confirmed |
| SLI-RULE-017 | The basic-search function applies string-escaping to the search string as its very first operation, before any of its branches concatenate it into SQL — the one search-input path specifically checked for injection risk, and it is consistently protected. | Every basic-search submission from this module's list view (and every other module reusing this shared function) | Basic-search where-clause construction | N/A — confirms a safe pattern | Confirmed |
| SLI-RULE-018 | The advance-search criteria-building function applies **no escaping of its own** — several of its branches concatenate the search string raw into comparison operators; this function's safety is entirely dependent on its callers having pre-escaped the value, which both of its currently-traced callers do — but the function provides no defense of its own, so any future or currently-unaudited caller that passes an unescaped value through would be directly injectable. | Advance-search submissions with several specific criteria types | Advance-search where-clause construction | Not directly exploitable via the two callers traced; flagged as a latent injection surface with no internal guard | Confirmed |
| SLI-RULE-019 | The dashboard-drill-through where-clause builder mixes two protection levels in the same function: several parameters are correctly quoted before concatenation, but four other parameters (campaign id, quote id, invoice id, purchase-order id) are taken straight from the request and concatenated with **no quoting, no escaping, and no numeric cast** — this branch is reachable from this module's own list view whenever the dashboard-drill request type is present, making it a second live, unmitigated SQL injection vector in this module's shared search infrastructure, reachable through the module's own everyday list-rendering path rather than a specific dismiss-button click. | Dashboard-widget drill-through clicks that route through this module's list view with the relevant request parameters | Dashboard-drill where-clause construction | **Critical (security) — confirmed SQL injection, no mitigation, on 4 of 8 parameters in this function** | Confirmed |

## Open Questions

- **The full rule catalog with legacy-source file:line citations** is preserved at
  `blueprint/module/SearchLineItem/02-validation-rules.md` for traceability if a claim above ever needs
  re-verification against the original source.
- Beyond the two confirmed Critical injections above, the blueprint's later risk-re-verification pass
  found one second-order (low-exploitability) unparameterized query, one unresolved shared-framework
  boundary, and confirmed no `eval`/`base64_decode` usage anywhere in the module — see
  `risks-and-open-questions.md` for the full risk register.
- **Whether the alert-dismiss action's missing permission check (SLI-RULE-014) is intentional design**
  (every authenticated user is meant to be able to dismiss any supersede/return alert) or a genuine gap
  is not resolvable from static analysis alone — flagged for subject-matter-expert confirmation. See
  `risks-and-open-questions.md` §9.4.
