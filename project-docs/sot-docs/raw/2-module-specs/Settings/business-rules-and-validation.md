# Settings — Business Rules & Validation

> Every rule gets a stable ID (e.g. <MOD>-RULE-001) so Stage 4's test docs can trace back to it.

Source: `docs_from_blueprint/module/Settings/03-business-rules-and-validation.md`, itself sourced from
`blueprint/module/Settings/02-validation-rules.md` ("Pass 2 — Settings Validation & Business Rule
Catalog"). The blueprint catalogs **209 numbered business/validation rules** (source IDs SET-VAL-001
through SET-VAL-209), mapped below to `SET-RULE-001` through `SET-RULE-209` with no gaps and no
range-summarization — every rule is itemized individually, matching the source's own continuous
sequential numbering. Given the module's exceptional scale (236 files), the source pass was
deliberately scoped to the Save/Add/Edit/Delete/validate-shaped files most likely to contain real
business-rule enforcement, not exhaustively every read-only file among the 236 — this scoping
constraint is inherited here, not resolved. The full rule catalog with exact file:line legacy citations
remains available at `blueprint/module/Settings/02-validation-rules.md` for re-verification.

**Confidence** column: **Confirmed** where the source states the finding as directly confirmed by
reading the live code/schema (most rules below — this was a code-reading pass, not inference from
prose); **Inferred** where the source itself flags the claim as unconfirmed, structurally-implied-but-
untested, or dependent on an unread caller/file.

## 3.0 Headline results (module-wide, carried through every rule below)

- **SQL-injection streak: confirmed across every one of the seven concern areas, an unbroken 8-for-8
  streak** (every module blueprinted in this series has found at least one confirmed injection). This
  module alone contributes dozens of confirmed raw-request-into-unescaped-SQL findings, including
  several **identifier-position** injections (raw table/column names taken directly from request data,
  not just values) and at least one completely unquoted, unescaped raw interpolation
  (SET-RULE-201).
- **`updateOrganizationDetails.php`** (§3.1): both the target column name and the value written to the
  organization's single profile row are taken directly from the request with no allow-list and no
  escaping; the call is parameterized in form only.
- **`SaveCustomLabels.php`** (§3.1): the three hardcoded field-label updates have no module-scope
  filter, and the recordid-to-fieldname mapping is never cross-checked at execution time.
- **Module Manager Restore/Delete asymmetry** (§3.3): a real, high-severity bug — Delete performs a
  genuine hard delete across every table a module registers, while Restore only ever flips a
  soft-delete flag on at most two tables and never re-inserts data. Because Delete removes the rows
  before Restore's own lookup can match them, Restore is structurally incapable of undoing a Delete
  performed through this tool, yet still reports false success.
- **Two dead-table bugs** (§3.4): one gateway-config bug exists in one dead (commented-out) form and
  one live, dispatch-reachable form not previously flagged; a second sits in a live delete branch,
  meaning deleting that credential always fails, leaving stale tokens live indefinitely.
- **`managedivision.php`'s wrong-column duplicate-check bug** (§3.5): fully traced through the database
  driver's own error handling — the query against a nonexistent column fails silently, the row-count
  read returns PHP `NULL`, and `NULL == 0` evaluates `true` under PHP's loose comparison, so duplicate
  division names are **never** blocked, on every single invocation.
- **`SaveRole.php` orphan-profile bug** (§3.2): every role *edit* through this action unconditionally
  inserts a brand-new, permanently orphaned profile-permission row set, while the real update is dead
  code in this file (handled instead by a different module's file).
- **Base-currency lock** (§3.6): the only Base-currency protection found anywhere is a client-side
  `disabled`/`readonly` HTML attribute on the edit form — the currency-save action itself has no
  server-side guard, and the currency-delete action performs an unconditional delete with no
  Base-currency check at all.
- **Central save-dispatch mechanism** (§3.7): the module-wide generic settings-save file is confirmed to
  have no meaningful validation-before-write as a matter of design — the bulk of its ~35 sections fall
  through to a generic, schema-blind writer with no domain/type checking of any kind.
