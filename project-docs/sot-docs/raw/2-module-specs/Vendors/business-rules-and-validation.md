# Vendors — Business Rules & Validation

> Every rule gets a stable ID (e.g. <MOD>-RULE-001) so Stage 4's test docs can trace back to it.

Source: `docs_from_blueprint/module/Vendors/03-business-rules-and-validation.md`, itself extracted from
`blueprint/module/Vendors/02-validation-rules.md`. Original rule IDs (`VEN-VAL-###`) are renumbered
`VEN-RULE-###` 1:1 (VEN-VAL-001 → VEN-RULE-001, etc.) for this template's ID scheme; the mapping is
1:1 in numeric order, no rules split, merged, or dropped. Original file:line legacy citations are dropped
here (traceability detail, not needed for a forward-looking spec) but remain available in
`blueprint/module/Vendors/02-validation-rules.md` if a rule ever needs re-verification.

**Severity legend**: *Hard block* = the operation is refused/rejected entirely; *Guard/scope-gate* = a
sub-step or side effect is conditionally skipped, not the whole operation; *Clamp/auto-correct* = a value
is silently adjusted rather than rejected; *Not a block* = documents a computation branch, a
duplicate/no-op assignment, or a side-effect gate, not a validation per se.
**Confidence**: Confirmed (explicit source, read and traced) / Inferred (deduced, needs verification).
Nearly all 48 rules below are Confirmed — each was extracted from a direct source-code read; the few
Inferred rows are called out individually where the source itself flags reduced certainty (e.g. an
unread/unconfirmed downstream function).

## Open Questions

- **Headline finding 1**: The "Primary Supplier" cache field is confirmed dead — nothing in the module's
  save paths writes to it, and the edit screen doesn't even read it. Corrects any prior characterization of
  it as an actively-maintained cache. (See `entities-and-fields.md`.)
- **Headline finding 2**: Line-code uniqueness is enforced only as an optional client-invoked ajax
  pre-check (VEN-RULE-010/011) — never at actual save time. A save submitted directly (bypassing the
  client-side pre-check) can set a duplicate Line Code with no server-side rejection at all.
- **Headline finding 3**: Primary-supplier assignment is procedurally one-per-(vendor, location), not
  DB-constraint-backed, and has a live SQL-precedence bug (VEN-RULE-041) that can leak deleted/self/
  cross-scope vendors into the candidate list — though the specific literal this bug depends on has been
  structurally unreachable since a 2017 picklist rename.
- **Headline finding 4**: The QuickBooks sync queue is only partially dead — the create path is live, the
  edit path is dead (VEN-RULE-045). Every vendor edit builds the full QuickBooks payload and reaches the
  queue object but never actually enqueues it.
- Whether `SaveVendorLinecodeDescription.php`'s missing vendor-scoping (VEN-RULE-025) is a genuine bug or
  reflects an intentional design where "line code description" is meant to be a shared, cross-vendor
  attribute — needs SME confirmation before a rewrite either preserves or corrects this behavior (see
  `risks-and-open-questions.md` for the full framing).
- Whether the six satellite tables are actually cleaned up on vendor delete (VEN-RULE-022) beyond the
  confirmed SlipStream-scoped callee — unresolved.
- Whether the owning module's (`VendorLinecode`) default-row/default-door-code exclusivity updates are
  intended to be system-wide or per-vendor — unresolved, relevant to VEN-RULE-025's design-intent question.
- 24 systemic bug/defect/security findings were surfaced across all source passes and are covered in
  `risks-and-open-questions.md`, not restated here.
