# Vendors — Cross-Module & Integration Touchpoints

Source: `docs_from_blueprint/module/Vendors/07-cross-module-integrations.md`, itself derived from
`blueprint/module/Vendors/06-cross-module-integrations.md`. Described as capability/data-contract needs —
what crosses each boundary and in which direction — not as any specific integration protocol or
technology. Vendors' cross-module footprint is narrower and more targeted than a "blanket join on every
table" module: modules that place orders with, pay, or classify suppliers read it, but no module reads
Vendors data as unremarkable background radiation.

## Related Modules

| Module | What This Module Reads | What This Module Writes/Triggers | Direction | Sync/Async |
|---|---|---|---|---|
| PurchaseOrder | Vendor identity/classification for the primary-supplier line-code dropdown (hits the same dead classification-value bug documented in `workflows.md`); the cost-source-selector resolution (fanned out to at least four independent PO-line-build code paths); Freight PPD display data; primary-supplier/vendor-availability/EDI-eligibility gating; tax-exempt flag and tax-authority code for PO tax calculation. | A confirmed direct write into the Vendors header's own custom-field table — a Purchase-Order-module ajax endpoint runs raw update statements against the Freight PPD fields directly, bypassing Vendors' own entity/save machinery entirely. This is a third write path for fields Vendors' own two save paths already diverge on, and the least safe of the three: no coercion, confirmed SQL-injectable, no QuickBooks-push notification. | Bidirectional. | Synchronous, all ajax/inline at PO-entry-screen time. A specific header field ("last order date," hypothesized as a PO-write target) is confirmed genuinely dead — no code anywhere reads or writes it. |
| Products | Vendor Line Code's subline/product-division/door-configuration classification, read directly by Products' own product-detail rendering and door-configuration ajax action. The "Pull Cost Price From" resolver, read by Products' own B2B/catalog code — the vendor's cost-source configuration feeds both internal PO/SO pricing and the external-facing B2B catalog's displayed/computed cost. | Nothing found — every Products-side reference is a read. | Products → Vendors, read-only. | Synchronous, inline at Products page-render/ajax time. |
| VendorLinecode (a distinct module) | N/A from Vendors' perspective — VendorLinecode is a genuinely independent, full-CRUD owner of the shared Vendor Line Code table, not a display layer over Vendors' own writes. It instantiates its own entity, resolves posted linecode/subline/product-division names to ids, saves through its own entity-save machinery, then performs three additional raw-SQL writes (a default-row exclusivity update, the same pattern for a default-door-code field, and a direct DCS-fields write). It also owns a second table entirely outside Vendors' field catalog — a JSON-blob price-level table (`lbm_nonstockpricelevel`) keyed to the line code id. | Vendors' own narrow, description-only write into the same shared table. | VendorLinecode → shared table (full CRUD, primary owner); Vendors → same table (narrow write); Products → same table (read-only); SalesOrder's calculator → same table (read-only). | Synchronous, all four relationships inline request-time — no cron/batch component found for this table. |
| VendorInvoice | N/A — VendorInvoice reads Vendors' data to render its own screens (vendor name, a handful of header fields), not a two-way sync. No file under Vendors' own module references any VendorInvoice table. | Nothing. | VendorInvoice → Vendors, read-only FK reference (display/join only). | Synchronous, inline join at VendorInvoice page-render time. |
| RebateTracker | Reads vendor identity to scope its own rebate-rule listing/settings screens (joins the vendor tables, sorts by vendor name). A separate rebate-settings function scopes by line code via Products' line-code classification — an indirect, not direct, Vendors-table read. | Nothing — does not write back to any Vendors table. | RebateTracker → Vendors, read-only. | Synchronous, inline join at RebateTracker listview-render time. |
| Forecasting | Primary Supplier Assignment consumer, including exposure to the classification-value dead-code bug (`workflows.md`) in its fallback branch. | Nothing. | Forecasting → Vendors, read-only. | Synchronous, inline at Forecasting report-render time. |
| Settings (SlipStream admin) | N/A from Vendors' perspective. Settings owns the entire administrative/bulk side of the SlipStream vendor-sync relationship, none of it reachable from Vendors directly: bulk vendor import to SlipStream (admin-triggered batch, iterates a vendor-id list, calls the SlipStream import API, writes SlipStream configuration/account identifiers on success, logs every attempt to a SlipStream-specific log table outside Vendors' own catalog); the delete-disconnect callee; a bulk payment-import action against POReconciliation-domain data, entirely outside Vendors' scope. | Vendors owns the display-facing "SlipStream integration status" flag and the one initial-link write site — a narrower write than the bulk-import path, meaning two independent code paths can each move a vendor into the "Imported" state (individual link flow vs. admin bulk-import screen). | Bidirectional, asymmetric: Settings owns outbound admin/bulk writes; Vendors owns only the initial individual-link write and read-only display; the inbound webhook (below) is a third, neither-module-owned path. | Synchronous within each admin action's own request; asynchronous/externally-triggered for the webhook path. |

## External Systems

| System | What Crosses the Boundary | Direction | Trigger | Sync/Async |
|---|---|---|---|---|
| QuickBooks (OCS) | Per-record vendor sync: `VendorAdd` enqueue is live on every vendor creation; `VendorMod`/`VendorQuery` enqueue calls exist as code but the edit-path enqueue is confirmed commented out (VEN-RULE-045); the bulk "query back from QuickBooks" driver is live and separate again. | Bidirectional, asymmetric (create-path push live, edit-path push dead, query-back path live). | Vendor create, vendor edit (no-op), bulk sync-all action. | Synchronous per-record call at save time; the queue-drain mechanics (SOAP Web Connector consumer, polling/retry) were never read in any source pass. |
| EDI (Do It Best / Orgill / Emery Jensen Distribution) | The header's "Active EDI" field is not consumed by a dedicated EDI module — it is read directly by PurchaseOrder-module code at PO-creation and PO-finalize time to route/transmit the order through one of three named EDI providers (excluding RGN/return POs). Vendors' role is purely to store the provider selector and provider-specific vendor id / "allow to send via EDI" flags; all transmission logic lives in PurchaseOrder. | Live, actively-used, entirely owned and consumed by PurchaseOrder-module code — there is no separate dedicated EDI module. | PO creation, PO finalize. | Synchronous, at PO-creation and PO-finalize time. |
| Saberis | Two vendor-level configuration fields (suspected label/column-name swap, see `entities-and-fields.md`) feed a fallback UOM-group/NS-code default when a buyout SalesOrder line item needs a new Non-Stock Part record created on the fly and no explicit UOM-group/NS-code was supplied — with a further fallback to a system-wide default if the vendor has none set. | Live, consumed at SalesOrder/buyout non-stock-part creation time. | SalesOrder buyout non-stock-part creation. | Synchronous, inline. |
| Aconnex | Two structurally different mechanisms share the "Aconnex" name — not the same mechanism: (a) two vendor-level fields (Seller ID / Customer #) are one of several alternate signals a shared vendor-detail-loading function checks to decide whether any EDI transmission channel is configured, gated by an "allow buyout PO via EDI" flag; (b) the actual PO-to-Aconnex transmission trigger does not read those fields at all — it reads a PurchaseOrder-owned column and calls a PurchaseOrder-owned transmission function. Whether that transmission function itself reads the vendor-level fields internally was not traced. | Vendors supplies EDI-availability signal fields; the actual outbound transmission is entirely PurchaseOrder-owned. | EDI-availability check, PO transmission. | Synchronous, inline. |
| X12 EDI | Three vendor-level configuration fields present in the schema — no consumer found anywhere in a repo-wide search. Not verified with the same rigor applied to a confirmed-dead field elsewhere in the catalog. | Unconfirmed — likely dead, not proven dead. | N/A | N/A |
| TecOrder | A vendor-level seller-id field is checked (alongside a row-count lookup against a separate TecOrder-credentials function) as one more signal in the same "is any EDI channel configured" determination the Aconnex fields feed. The broader TecOrder integration (a cross-module location-mapping table) was already flagged as unread/untraced by a sibling module's own cross-module pass. | Vendors supplies one confirmed EDI-availability signal field; the full integration surface not traced. | EDI-availability check. | Synchronous, inline. |
